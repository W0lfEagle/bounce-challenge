# Current decisions

These are the decisions behind the submitted solution. Git history preserves earlier milestones; this document describes current behavior.

| Decision | Reason | Tradeoff or boundary |
| --- | --- | --- |
| TypeScript, Expo/React Native, web delivery | One typed frontend; web is straightforward for reviewers to run. React Native preserves an option for future native clients. | Native builds and durable native recovery require further work. A web-only React app would use fewer platform dependencies. |
| Fastify with route, service and query functions | HTTP concerns, checkout policy and SQL have distinct responsibilities. Functions receive dependencies explicitly. | The extra files cost navigation, so the README links the checkout service directly. No dependency injection framework or repository classes. |
| SQLite and plain parameterized SQL | Local persistence needs no external service. Short transactions make payment claiming and confirmation explicit. | Synchronous queries block the API process; larger workloads would need reassessment. The native driver requires consistent Node versions. |
| Shared Zod contracts | The server validates requests and database responses; the client validates API responses. Types come from the same schemas. | The shared workspace needs rebuilding after changes. Database models remain server-only. |
| USD integer cents and server-owned pricing | The provider receives an authoritative amount without floating-point arithmetic. The client sends the terms the customer saw for comparison. | A changed price or quantity bound requires the customer to review and Book again. One bag item and USD are deliberate scope limits. |
| Basic card structure validation | The mock requires only a card number; 13–19 digits and ordinary spaces keep the implementation small. Formatting on blur preserves cursor behavior. | No checksum, brand, expiry or CVC validation. This is not a production card collection integration. |
| Separate checkout and payment-attempt IDs | Replay returns an existing result; an explicit decline can retry with a fresh attempt. Accepted booking details remain immutable. | Non-card edits after decline start a new checkout. A card change needs only a new attempt. |
| Claim → provider → persist | A short SQLite transaction claims work before the network call. Another transaction saves the payment result and confirmation together. | The provider and database cannot share a transaction. A lost provider response or failed save can remain unknown. |
| Preserve processing and uncertainty | Recovery uses read-only GET requests. A running payment is locked while bounded status checks wait for its result. | No documented provider lookup/idempotency API exists to reconcile every uncertain charge. |
| Mock-only Start over after unknown | A reviewer can continue the demo after an unresolved mock payment. The old attempt retains replay protection. | A separate checkout may create another mock transaction; this is a conscious demo limitation. |
| Clear recovery IDs after acknowledged success | Reload starts a fresh form, making repeated demonstrations simple. Database records remain intact. | A saved success is recovered once; there is no booking history UI. |
| Checkout coordinator, local form state and small policy/mechanism helpers | `Checkout.tsx` keeps submission, accepted terms and outcome decisions visible. `CheckoutForm.tsx` owns fields, validation and presentation; attempt selection and cancellable polling have focused helpers. | Six form props describe the boundary. The form stays mounted through pending/failure states and unmounts on success. No routing, global state, form engine or state-machine library. |
| Jest plus three browser smoke checks | Isolated tests cover failures and edge cases; browser checks exercise the boundaries together. | The browser suite is deliberately small and replaces only the external provider. Live-provider behavior can differ. |

The single-store exercise does not require native deployment, multiple product types, authentication, elaborate styling, or a production reconciliation console. Adding those would increase the explanation and maintenance burden without strengthening the required flow.
